1. 文档目的

本文档面向项目维护者、二次开发者和部署人员，说明 XHS_ALL_IN_ONE 的整体框架、模块边界、核心业务流程、数据模型、安全设计和扩展方式。内容基于当前仓库代码结构编写，重点描述系统如何从小红书账号接入、数据采集、内容入库、AI 创作、素材处理到发布与自动运营形成闭环。

2. 项目定位

XHS_ALL_IN_ONE 是一个小红书一站式智能运营平台，目标是把以下能力整合到同一个 Web 产品中：

  • 多账号管理：PC 端账号、Creator 创作者账号登录、Cookie 导入和健康检查。
  • 数据采集：关键词搜索、URL 抓取、用户笔记抓取、评论抓取和素材下载。
  • 内容资产管理：统一内容库、标签、评论、素材、导出。
  • AI 创作：笔记改写、标题生成、标签生成、图片生成、封面生成、图片描述。
  • 发布管理：草稿进入发布中心、素材上传 Creator、立即或定时发布。
  • 自动运营：按关键词和频率自动搜索、改写、上传、发布。
  • 数据洞察与竞品监控：统计概览、热点、趋势、监控目标刷新和快照。

系统当前以小红书 xhs 为已启用平台，平台注册表预留了抖音、快手、微博、闲鱼、淘宝等后续扩展位。

4. 技术栈

4.1 后端

  • Python 3.10+
  • FastAPI：HTTP API、认证依赖、OpenAPI 文档。
  • Uvicorn：ASGI 运行时。
  • SQLAlchemy 2.x：ORM 和数据库访问。
  • Alembic：数据库迁移。
  • Pydantic / pydantic-settings：配置和数据校验。
  • APScheduler：定时发布、监控刷新、账号 Cookie 巡检等后台任务。
  • cryptography Fernet：Cookie 和 API Key 加密。
  • PyExecJS、Node.js、根目录 static/*.js：小红书签名相关执行环境。
  • requests、aiohttp：平台接口请求。
  • Pillow、OpenCV、numpy：图片处理能力。

4.2 前端

  • React 19
  • TypeScript
  • Vite 7
  • React Router 7
  • Ant Design 6
  • Axios
  • dnd-kit：素材拖拽排序。
  • Recharts：数据图表。
  • lucide-react、Ant Design Icons：图标体系。

4.3 存储与部署

  • 开发默认 SQLite：./data/spider_xhs.db
  • 生产可切换 MySQL
  • 本地文件存储：backend/app/storage/media、backend/app/storage/exports
  • Docker 多阶段构建：先构建 Vite 前端，再复制到 Python 镜像并由后端静态托管。

5. 运行拓扑

5.1 本地开发模式

本地入口为根目录 main.py：

python main.py --with-frontend

启动过程：

  1. 解析 CLI 参数，默认后端监听 127.0.0.1:8000。
  2. 如果带 --with-frontend，进入 frontend/ 启动 Vite，默认端口 5173。
  3. 后端通过 Uvicorn 加载 backend.app.main:app。
  4. 前端使用 frontend/src/lib/api.ts，通过同源或代理访问 /api 接口。

5.2 容器和生产模式

容器入口为 Dockerfile：

  1. node:20-alpine 阶段执行 frontend 构建。
  2. python:3.11-slim 阶段安装 Python 依赖和 Node.js 运行时。
  3. 复制项目源码和 frontend/dist。
  4. 设置 FRONTEND_SERVE_STATIC=true，由 FastAPI 挂载构建后的前端资源。
  5. 健康检查访问 http://localhost:8000/api/health。

docker-compose.yml 默认启动单个 app 服务，并把数据、配置、媒体和导出目录映射到宿主机。MySQL 服务作为生产可选项保留在注释中。

6. 后端框架设计

6.1 应用入口

  • 在 lifespan 中执行 init_db()，启动时自动运行 Alembic 迁移或创建表。

  • 注册 CORS。

  • 挂载所有业务路由。
  • 生产模式下，使用 StaticFiles 托管 frontend/dist，并为非 API 路径提供 SPA fallback。

6.3 核心基础设施

配置系统

backend/app/core/config.py 使用 Settings 统一管理配置，加载顺序为：

  1. config/default.yaml
  2. CONFIG_FILE 指定的 YAML
  3. .env
  4. 环境变量

关键配置包括数据库连接、JWT 与 Fernet 密钥、服务监听地址、CORS、调度器开关和前端静态托管路径。

数据库与迁移

backend/app/core/database.py 提供全局 SQLAlchemy engine 和 SessionLocal。启动时会创建 SQLite 数据目录，执行 Alembic 迁移；在 Alembic 不可用时回退到 Base.metadata.create_all()。该模块还包含模型名称规范化和 SQLite 时间字段向 Asia/Shanghai 对齐的兼容性处理。

安全与加密

backend/app/core/security.py 提供 PBKDF2-SHA256 密码哈希、HMAC-SHA256 令牌、Access Token、Refresh Token 和 Fernet 加解密能力。Access Token 默认 15 分钟过期，Refresh Token 默认 7 天过期。Cookie 和 API Key 等敏感信息通过 Fernet 加密。

平台注册

backend/app/core/platforms.py 定义平台枚举和平台元信息。当前 xhs 启用，其它平台以 coming_soon 形式存在，前端可通过 /api/platforms 读取该注册表并展示平台入口。

6.5 XHS 适配层

backend/app/adapters/xhs/ 是 Web 后端和底层 SDK 的隔离层：

  • pc_api_adapter.py：封装 PC 端搜索、笔记详情、评论、用户笔记、自身账号信息。
  • creator_api_adapter.py：封装 Creator 话题、地点、素材上传、发布、已发布作品。
  • pc_login_adapter.py、creator_login_adapter.py：封装二维码和手机登录流程。
  • request_env.py：在直接请求 XHS 时临时处理代理环境，避免系统代理干扰底层 SDK。

上层 API 不直接依赖 apis/ 的具体实现，而是通过 adapter 调用。这样可以把签名、Cookie 转换、逆向请求等易变逻辑限定在适配边界内。

7.3 API 客户端和认证态

frontend/src/lib/api.ts 统一封装后端请求：

  • Axios 实例默认 baseURL 为 /api。
  • Access Token 存在模块内存中。
  • Refresh Token 存在 localStorage 的 spider_xhs_refresh_token。
  • 请求拦截器自动添加 Authorization: Bearer <token>。
  • 响应拦截器在 401 时尝试刷新 Access Token。
  • 刷新失败时清空登录态并提示重新登录。

前端业务页面只调用 api.ts 中的函数，不直接拼接底层请求细节。

8.3 数据隔离规则

后端大多数业务表都有 user_id 字段，API 层通过 get_current_user 获取当前用户，并在查询、更新、删除和执行操作时强制用户范围过滤。跨用户访问通常返回 403 或 404，避免账号、笔记、草稿、发布任务、监控目标等资源被越权访问。

9. 核心业务流程

9.1 登录认证流程

sequenceDiagram
    participant UI as 前端
    participant API as /api/auth
    participant DB as users

    UI->>API: register 或 login
    API->>DB: 查询或创建用户
    API->>API: 校验密码，生成 access_token 和 refresh_token
    API-->>UI: 返回令牌
    UI->>UI: access token 存内存，refresh token 存 localStorage
    UI->>API: 后续请求携带 Bearer token
    API->>API: decode_token 并加载当前用户

9.2 平台账号接入流程

账号接入有三条路径：

  • 二维码登录：创建 LoginSession，返回二维码，前端轮询，确认后保存账号和 Cookie。
  • 手机验证码登录：发送验证码，确认后保存账号和 Cookie。
  • Cookie 导入：前端粘贴 Cookie，后端解析并执行账号资料刷新。

落库策略：

  1. PlatformAccount 保存账号基本资料、平台、子类型、状态和资料 JSON。
  2. AccountCookieVersion 保存加密 Cookie，每次登录或导入创建新版本。
  3. 健康检查通过 adapter 调用平台自我资料接口，更新账号状态和资料。

9.3 笔记采集到内容库流程

flowchart TD
    A[选择 XHS PC 账号] --> B[关键词搜索或 URL 抓取]
    B --> C[XhsPcApiAdapter 调用 apis SDK]
    C --> D[API 归一化笔记结果]
    D --> E[前端展示发现列表或抓取结果]
    E --> F[批量保存到内容库]
    F --> G[notes 主表 upsert]
    G --> H[保存 note_assets 和 note_comments]
    H --> I[可打标签、导出、进入草稿]

设计要点：

  • 搜索、详情、评论等 XHS 原始结果会在 API 层被归一化为前端可消费结构。
  • 内容库按当前平台用户隔离，不绑定某个单一 XHS 账号。
  • 保存笔记时可刷新重复笔记，避免同一外部 note_id 重复堆积。
  • 媒体可以只保留远程 URL，也可以下载到本地 storage/media。

9.4 内容库到 AI 草稿流程

flowchart LR
    Note[内容库 Note] --> Draft[AiDraft]
    NoteAsset[NoteAsset] --> DraftAsset[DraftAsset]
    Draft --> AIRewrite[AI 改写/标题/标签]
    AIRewrite --> Draft
    Draft --> ImageAI[AI 图片生成/封面/描述]
    ImageAI --> GeneratedAsset[AiGeneratedAsset]
    GeneratedAsset --> DraftAsset

设计要点：

  • AiDraft.source_note_id 记录草稿来源。
  • 草稿正文、标题、标签和素材顺序可独立编辑。
  • 文本和图片 AI 都通过 ModelConfig 选择默认模型。
  • API Key 使用 Fernet 加密存储。

发布状态通常围绕以下阶段变化：

  • pending：待发布。
  • scheduled：定时发布待执行。
  • running：正在上传或发布。
  • published：发布成功。
  • failed：发布失败，可重试。
  • cancelled：用户取消。

9.6 定时任务和自动运营

scheduler_service.py 统一承担后台周期任务：

  • 执行到期的 PublishJob。
  • 刷新到期的 MonitoringTarget。
  • 执行到期的 AutoTask。
  • 定期检查账号 Cookie 健康状态并生成通知。

自动运营任务的典型流水线：

  1. 根据 AutoTask.keywords 选取关键词。
  2. 使用 PC 账号搜索热门笔记。
  3. 将候选内容保存或转为草稿。
  4. 通过默认文本模型改写标题和正文。
  5. 复制或处理素材。
  6. 使用 Creator 账号创建发布任务并发布。
  7. 更新 total_published、last_run_at、next_run_at。

9.7 监控和分析流程

监控目标支持关键词、账号、品牌、URL 等类型。刷新时会：

  1. 选择目标指定账号或用户可用 PC 账号。
  2. 根据目标类型抓取最新内容。
  3. 将匹配笔记保存为内容库记录。
  4. 生成 MonitoringSnapshot。
  5. 累计失败时记录错误并可触发通知。

分析接口基于当前用户的内容库、标签、评论、监控目标和关键词分组生成统计视图，包括概览、Top 内容、热点主题、互动趋势、关键词趋势、评论洞察和导出报告。

10. 配置设计

10.1 默认配置

  • 后端监听 0.0.0.0:8000。

  • 数据库类型为 MySQL。

10.3 配置优先级

config/default.yaml < CONFIG_FILE 指定文件 < .env < 环境变量

11. 安全设计

11.1 认证和会话

  • 用户密码不明文保存，使用 PBKDF2-SHA256 哈希。
  • Access Token 短期有效，Refresh Token 长期有效。
  • 前端 Access Token 存内存，降低本地持久化泄露面。
  • Refresh Token 存 localStorage，接口 401 时自动刷新。

11.2 敏感信息加密

  • XHS Cookie 使用 AccountCookieVersion.encrypted_cookies 加密保存。
  • 模型 API Key 使用 ModelConfig.encrypted_api_key 加密保存。
  • Fernet key 可显式配置，未配置时从 secret_key 派生。

11.3 权限边界

  • 后端 API 以当前 User 为核心权限边界。
  • 所有账号、笔记、标签、草稿、发布、任务、通知、模型配置、监控和自动运营数据都需要用户范围过滤。
  • 对跨用户资源执行读取、修改、删除或运行时调用时，应返回拒绝或不存在。

11.4 外部平台调用隔离

  • XHS SDK 调用集中在 backend/app/adapters/xhs/。
  • direct_xhs_request_env() 用于控制直接访问 XHS 时的请求环境。
  • 上层业务不直接操作签名 JS 和逆向请求细节。

12. 文件和资产设计

12.1 媒体文件

媒体文件主要存放在：

backend/app/storage/media

典型来源：

  • 用户上传的图片或视频。

  • AI 生成图片。

  • 抓取结果导出。

后端通过 /api/files/exports/{file_name} 提供下载。

13. 平台扩展设计

后续新增平台时，建议按以下顺序扩展：

  1. 在 backend/app/core/platforms.py 添加或启用平台元信息。
  2. 新增 backend/app/adapters/<platform>/，隔离该平台 SDK 或 API 细节。
  3. 新增 backend/app/api/platforms/<platform>/ 路由模块。
  4. 复用通用表：platform_accounts、notes、ai_drafts、publish_jobs、tasks。
  5. 在前端 frontend/src/pages/platforms/<platform>/ 添加平台页面。
  6. 在 frontend/src/app/router.tsx 接入路由。
  7. 在 frontend/src/lib/api.ts 添加平台 API 客户端函数。
  8. 添加后端测试，覆盖账号归属、跨用户拒绝、平台调用适配和核心业务流。

扩展时应保持两个边界：

  • 平台差异放在 adapter 和平台专属 API 中。
  • 内容库、草稿、发布、任务、通知、模型配置尽量复用通用模型。

14. 测试和质量保障

当前测试主要位于 tests/backend/，覆盖范围包括：

  • 根目录启动参数解析和前端启动命令。
  • 健康检查和平台注册表。
  • 数据库初始化、Alembic 迁移和兼容性迁移。
  • 用户注册、登录、刷新令牌和认证失败。
  • XHS 二维码登录、手机登录、账号导入和健康检查。
  • XHS 搜索、详情、评论、抓取和归一化。
  • 内容库保存、资产、评论、标签、导出和跨用户隔离。
  • AI 模型配置、文本生成、图片生成和资产作用域。
  • 发布任务、发布素材、上传、发布、定时、重试、取消。
  • 调度器、到期任务、自动刷新和通知。
  • 监控目标、分析、关键词趋势和竞品草稿。
  • 前端关键页面源码约束，例如 Ant Design 使用、页面功能保持等。

推荐的基础校验命令：

如果只修改文档，可执行文件存在性和 HTML 可读性校验；如果修改后端或前端业务代码，应至少运行对应后端测试和前端构建。

15. 设计约束和维护建议

  • 不建议业务层直接调用根目录 apis/，应通过 backend/app/adapters/。
  • 不建议在前端页面中散落 Axios 请求，应集中到 frontend/src/lib/api.ts。
  • 新增持久化表时应同步添加 SQLAlchemy 模型和 Alembic 迁移。
  • 新增用户资源时必须带 user_id 或明确的归属校验。
  • 新增外部平台调用时必须记录失败状态，避免后台任务无声失败。
  • 调度任务应写入 tasks 或更新业务状态，便于任务中心审计。
  • 涉及 Cookie、API Key、Token 的数据必须加密或短期化。
  • 自动运营、发布和监控属于高风险外部调用，应优先增加可重试、可取消、可观测状态。
  • 前端新增页面时应接入 ProtectedRoute 和 AppShell，保持统一导航和登录态。

16. 当前框架总结

当前项目采用清晰的前后端分离架构：React/Vite 提供运营控制台，FastAPI 提供统一业务 API，SQLAlchemy 负责持久化，APScheduler 承担定时任务，XHS 平台能力通过 adapter 层隔离到底层 SDK。核心业务围绕 User 做数据隔离，围绕 PlatformAccount 接入外部账号，围绕 Note -> AiDraft -> PublishJob 形成内容生产和发布闭环。

该框架适合继续向两个方向演进：

  • 横向扩展更多平台：通过平台注册表、adapter、平台 API 和前端平台页面扩展。
  • 纵向增强自动运营：在现有任务、通知、发布、监控和 AI 模型配置基础上增强调度策略、失败恢复和效果评估。
